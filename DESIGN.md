# Vision AI Studio Design System

## Overview

This is an as-built context seed, recorded from the existing PR18 implementation
and its narrow project-readiness repair. It does not introduce a rebrand, new
permission policy, runtime tokens, or a claim that every legacy screen conforms.

The product register is an inspection workbench: dark instrument-panel surfaces,
small operational readouts, persistent step navigation, and explicit saved-state
gates. Operators prepare images, label, train, evaluate, build an inspection flow,
and run inspections. The application name is **Vision AI Studio**; the repository
and development documentation also use **Modu Vision**.

The recognizable signature is the six-step navigation with annunciator-style
status colors. Task names, recovery, evidence, and readable controls take priority
over decoration. The existing interface is a dense workbench rather than a
marketing landing page; illustration-heavy or playful presentation is not its
established register. Manufacturing inspection is the documented domain; locale
alone does not establish a country-specific market or regulatory claim.

The implemented language type is `ko | en`, owned by
`src/renderer/types/index.ts` and `useProjectStore`; `WizardHeader` exposes the
language switch. Korean is the dominant content language. Some screens still use
Korean literals, so the switch is not evidence of complete English localization.
There is no Japanese-localization or native-language acceptance claim here.

- `src/renderer/styles/theme-light.css` is generated by
  `scripts/generate_light_theme.cjs`; do not hand-edit its theme mappings.
- Browser and installation limits are recorded in `docs/local-browser.md` and

The local browser runner uses HTTPS on localhost with local accounts and a
headless native helper. It is not a LAN hosting contract. The documented Windows
web runner is blocked pending private-key ACL validation; Linux runtime execution
is unverified. Desktop packaging targets require their own native acceptance.
The observed macOS/Chromium checks do not establish mobile or all-OS support.

## Colors

The chassis, panel, card, and border tokens above come from `index.css` and its
Tailwind aliases. White/cool-gray text forms the main hierarchy. Green, amber,
red, blue (`#3B82F6`), and offline gray (`#4B5563`) are operational annunciator
colors, accompanied by text/status rather than standing alone as meaning.

Workspace primitives use a distinct existing semantic palette in
`design-tokens.css`: background `#101722`, surface `#182332`, inset `#0d141e`,
border `#405166`, text `#edf2f8`, muted `#afbdce`, accent `#9cddff`, and focus
`#7dd3fc`. Their success/warning/danger text is `#9ce5bc` / `#ffd28a` / `#ffb5bd`.
These softer workspace colors are not replacements for the chassis status LEDs.

The generated light adapter changes surfaces and contrast while preserving
semantics: chassis `#F8FAFC`, surface/card `#FFFFFF`, border `#CBD5E1`, text
`#0F172A`, workspace accent `#0369A1`, focus `#0284C7`, success `#047857`, warning
`#B45309`, and danger `#B91C1C`. Existing screen-specific color literals remain;
this seed does not certify their contrast or theme coverage.

## Typography

The body uses the local Pretendard Variable font and Korean-capable system
fallbacks from `index.css`. Tailwind's `font-mono` stack is recorded separately
above; it does not imply every listed font is bundled. Numerical readouts use
tabular figures. The existing CSS floors older tiny console classes at 12px,
sets `text-xs` to 13px/20px, and raises small simple-view copy to 13px.

Workspace tokens define small/body/title at `.8125rem` / `.875rem` / `1.125rem`.
`product-workbench` uses 14px with 1.5 line height. Korean body text uses
`word-break: keep-all`; paths and technical identifiers may wrap explicitly.
Large-monitor root sizing changes at 1920px and 2400px. These declarations do
not substitute for actual zoom, fallback-font, or localization review.

## Layout

The application shell owns the viewport; its content panels own scrolling.
Workspace dialogs cap width at 72rem and height at `100dvh - 2rem`, with a
scrollable body and fixed header. Their grid uses auto-fit columns with a 22rem
minimum; the existing 600px breakpoint reduces dialog padding. The recorded
quarter-rem spacing scale belongs to workspace primitives, not every old screen.

Step 2 has a compact toolbar adaptation below 1439px width or 820px height.
Do not infer complete phone support from that adaptation. Preserve each panel's
scroll owner when changing its state; a table's sizing does not establish the
layout of a sibling form.

## Elevation & Depth

Hierarchy uses tonal surfaces and 1px borders. Workspace overlays use a dark
scrim and a `0 24px 80px #0008` shadow; nested workspace dialogs derive their
layer above the opener. The normal workbench relies on separation and status
instead of decorative blur or additional floating surfaces.

## Shapes

Workspace containers use `.625rem` corners, controls `.4rem`, and badges a pill
radius. Legacy Tailwind radii coexist with these primitives. Lucide outline
icons accompany operational labels; this seed does not change their stroke or
introduce another icon family.

## Components

### Canonical project-readiness behavior

| Capability | Canonical owner | Source of truth | Allowed variants | Verification |
| --- | --- | --- | --- | --- |
| Project-changing controls | `projectSwitchRefusal` and `subscribeProjectSwitchRefusal` in `useProjectStore.ts` | Existing running-operation and save guards, also called by `saveOpenEdits` | `ProjectWorkspaceDialog` and `SharedProjectPanel` subscribe to the same predicate; initial `localAuthenticationOnly` login retains its existing exception | Deterministic component transitions and the original F064 browser A/B/A scenario; see the repair evidence below |
| Select/Listbox | Existing native HTML select in `SharedProjectPanel` | Current platform-owned popup behavior and account/project selection handler | Native popup; no authored popup geometry or all-platform acceptance is asserted | Existing component selection/authority tests and browser scenario |
| Workspace overlay | `WorkspaceDialog.tsx` | Existing focus entry/restoration, Tab boundary, Escape and portal implementation | Nested workspace layer above its opener | Existing project/workspace component and browser coverage; not a universal legacy-dialog certification |
| Scrollbar | Global rules in `index.css` | Existing WebKit track/thumb/hover rules | Component-owned geometry may differ | Static inspection only in this repair; standards-based baseline completeness is an existing gap |

The project refusal predicate covers model-assist operations, batch inspection,
dataset load/split/generation, training, and flow run/load/save. Shared project
controls also retain their existing local busy and project-busy checks. Display
readiness follows these guards; handlers continue to enforce them before requests.
This is not permission granted by an enabled control. Server/account/project,
registration, workspace, actor and transport checks remain authoritative.

During initial local authentication, inherited workbench busy state must not
prevent logging back in. The existing `localAuthenticationOnly` path is preserved;
it is not a general exception for switching projects or saving data.

### Forms, actions and feedback

Workspace controls have their existing minimum heights, visible focus outline,
hover treatment, disabled opacity and `not-allowed` cursor. Shared-project errors
use the existing inline `role="alert"`; underlying guards remain the fallback
if state changes after an affordance was rendered. Fields retain their names,
password masking and account scope. This repair does not change confirmations,
credential handling, roles, native dialogs, or legacy form conventions.

Workspace primary actions use the darker cyan primary token. Neutral, warning,
error and disabled states must keep their distinct operational meanings. Content
uses plain Korean task verbs and visible counts/paths; a completed UI request is
not evidence of training completion, deployment, or human approval.

### Motion and review limits

Existing tactile feedback is short (75–100ms). Global reduced-motion CSS reduces
animation and transition duration. The global scrollbar currently has WebKit
fallback rules; standards-based and forced-colors coverage is not fully proven.

The scoped repair evidence is preserved under
`.superpowers/sdd/2026-10-28-shared-project-readiness-fix/`: component RED/GREEN,
related suites, typecheck, renderer suite, and the original F064 browser fixture.
A local pass is not a hosted-regression result or a comprehensive accessibility,
keyboard-popup, theme/locale, phone, 200% zoom, or field acceptance result.

## Do's and Don'ts

- **Do:** Reuse canonical project-readiness subscriptions alongside unchanged
  request-time guards; keep initial authentication distinct from project adoption.
- **Do:** Preserve original images, labels, saved workflows and refusal reasons;
  describe saved results and evidence boundaries accurately.
- **Don't:** Introduce a screen-local duplicate busy model or a wait/retry that
  hides a rejected operation.
- **Don't:** Treat this as-built seed or a static audit as approval of unrelated
  legacy UI, platform parity, runtime accessibility, model quality, or deployment.
