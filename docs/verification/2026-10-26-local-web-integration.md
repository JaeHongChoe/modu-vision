브라우저 실행기와 공유 서버 보안 변경을 합친 소스
`069d9b269763bd0ea3b955c4b73f15c0e1287044`에서 **새 합성 데이터의 실제 기능 흐름을 한 번에 완료**했습니다.
macOS 27.0.1, 격리 Chromium 1243, 실제 `node scripts/local-web.cjs`와 직접 HTTPS/WSS를
사용했습니다. [해시·응답·ID 상세 JSON](2026-10-26-local-web-integration.json)에 근거를 기록했습니다.

## 실제 확인 결과

- 새 격리 계정을 지원되는 터미널 숨김 입력으로 설정한 뒤 기본 화면에서 로그인하고
  분류 프로젝트를 만들었습니다. ZIP 업로드·검증·채택 후 작업 소스 선택까지 다시 로그인하는
  우회 없이 진행했습니다. 프록시·네이티브 브리지·storage/온보딩 주입은 사용하지 않았습니다.
- 서로 다른 합성 PNG 16장, 정상/불량 각 8장을 디코딩했습니다. 정상→불량과 불량→정상
  라벨을 각각 저장해 유지하고 학습/검증/시험을 **10/4/2**로 나눴습니다.
- 공식 캐시의 전체 SHA를 확인한 ResNet18로 **CPU, 1 epoch, 64px, batch 2, 60초 예산**의
  실제 학습을 **1회** 실행했습니다. 학습 POST와 저장 학습 작업은 각각 **1개**이며,
  작업 ID는 `job_1793016799_c39704`입니다. 재시도나 추가 학습은 없었습니다.
- 작업 센터에서 그 완료 작업을 열어 시험 이미지 2장을 평가했습니다.
  평가 ID는 `evaluation_1eee761345fa483d8edae0cadcb35eda`이고 선택 데이터 중복은 없었습니다.
  **정확도 0%, 정상 1장 과검·불량 1장 미검**, 혼동행렬은 `[[0,1],[1,0]]`입니다.
  작은 합성 데이터의 기능 확인 결과이며 모델 품질·현장 성능 승인이 아닙니다.
- 표준 평가는 자동 장치 선택을 사용합니다. 전후 `/health`의 동일 resolver는 MPS를
  보고했습니다. 이는 개별 평가 장치 영수증이 아니며, 학습의 CPU 설정이 표준 평가 장치를
  고정한다는 주장은 하지 않습니다.

## 실제 HTTPS 보안 응답과 재시작

총 16개 응답 모두 `nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`,
`Content-Security-Policy: frame-ancestors 'none'`을 확인했습니다.

- 인증된 `wss://localhost:53154/ws/telemetry`에서 실제 `hardware_stats`를 받았습니다.
  소유 서버 종료와 소켓 닫힘 후 bind 대기 우회 없이 같은 포트로 재시작했습니다.

  같은 열린 페이지에서 새 하드웨어 프레임을 받았고, 기록된 최초/재연결 프레임은 **126/29개**입니다.

  이미지·라벨·분할과 모델/메타데이터/작업 영수증/평가/평가 이력의 SHA가 같았습니다.
  새 세션의 라벨 변경·복원도 실제 UI와 CSRF로 저장했습니다.
- 세션 쿠키의 Secure·HttpOnly·SameSite Strict 속성을 확인했습니다. 쿠키 값과 계정 비밀번호는

## 최종 쿠키 요청 경계 보완과 재확인

후속 리뷰에서 localhost의 다른 HTTPS 포트가 같은 사이트로 취급돼 Origin 없는 쿠키 GET을
보낼 수 있는 조건을 확인했습니다. `5212d8d7`은 localhost 실행기의 `/api` 쿠키 요청에
Origin이 없으면 브라우저가 보낸 단일 `Sec-Fetch-Site: same-origin`을 요구합니다.
없는 값·none·same-site·cross-site·중복 값은 거절하고, 명시된 신뢰 Origin·bearer 호출·
미인증 health·정적 파일·WSS의 기존 경로를 유지합니다. 일반 공유 서버 진입점 전체의
GET 쓰기/CSRF 정책을 고쳤다는 주장은 하지 않습니다.

기존 소스에서 새 거절 조건 17개가 실패하는 것을 확인한 뒤, 보완된 소스의 관련 Python
시험 **175/175**와 최종 helper를 포함한 전체 scripts **181/181**이 통과했습니다.
초기 scripts 4개 실패는 임시 폴더의 정규 경로 처리와 이미 더 일찍 거절하는 health
오류 기대값을 수정한 것이며 제품의 서명·라이선스·health 보호를 완화하지 않았습니다.
renderer **2,344/2,344**, 타입 검사·빌드·기존 서비스/근거 검사도 통과했습니다.

`df55d815`의 후속 실제 브라우저 확인에서는 Origin 없는 쿠키 GET에 브라우저의
`Sec-Fetch-Site: same-origin`이 들어가고 HTTP **200**으로 수락됨을 CDP의 실제 전송 정보로
확인했습니다. 같은 원래 작업과 저장 평가 이력, 이미지·라벨·분할·WSS를 읽었고 27개
보존 파일의 전후 해시가 같았습니다. 새 학습·재평가·라벨 쓰기는 하지 않았습니다.
위 학습·평가의 원래 HEAD `069d9b26`과 상태 해시는 바꾸지 않았습니다.

후속 측정 시도의 전체 실패 기록도 보존했습니다. 첫 시도는 Playwright에 요청 헤더가
보이지 않아 중단됐고, 둘째는 정상 동일 출처 확인을 마친 뒤 선택적인 다른 포트 이미지
응답을 기다리다 시간 초과했습니다. 그 시도들을 전체 통과로 바꾸지 않았습니다. 정상
브라우저 호환성 근거와 선택적 공격 요청의 실통신 상태 측정은 별도로 구분합니다.
독립 검토의 코드 지적은 모두 해소됐으며, 최종 원격 CI와 병합 상태는 PR 기록으로 별도
확인합니다.

마지막 제한된 CDP 측정은 같은 `df55d815` 코드에서 **통과**했습니다. 정상 화면의
쿠키 GET은 Origin 없이 `same-origin`으로 전송되어 실제 **200**, 별도로 소유한 HTTPS
localhost 다른 포트의 이미지 요청은 쿠키와 `same-site`를 동반해 실제 **403**이었습니다.
두 응답 모두 보안 헤더 4개를 유지했습니다. 브라우저의 `net::ERR_BLOCKED_BY_ORB`가
선택적 이미지 응답을 Playwright 화면 이벤트에서 볼 수 없었던 이유도 확인했습니다.

최종 측정 상태 SHA는 `aff24394aa1b3722d83d363b17d9da3e3195481968ea08d136820c4b2ad5638a`입니다.
이전 두 측정 실패는 보존했고, 마지막 측정에서도 새 학습·재평가·라벨 쓰기 없이 원래 작업과
평가 이력을 읽었습니다. 원래 상태 SHA·분할·이미지·라벨·저장 파일은 변하지 않았습니다.
소유한 제품 서버와 시험 HTTPS 서버는 종료하고 포트 닫힘을 확인했습니다.
