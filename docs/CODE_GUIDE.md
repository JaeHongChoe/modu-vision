# 코드 읽기와 리팩토링 검토

이 문서는 현재 코드의 진입점과 중요한 상태 구분을 설명합니다. 주석은 처리 순서의 이유와 유지해야 할 조건에 집중합니다. 아래 리팩토링 항목은 구조 검토 결과이며, 구현 완료나 확인된 버그 목록을 뜻하지 않습니다.

## 1. 먼저 읽을 파일

| 순서 | 파일 | 확인할 내용 |
| --- | --- | --- |
| 1 | [Electron 진입점](../src/main/index.ts) | 창 생성, preload 연결, 백엔드 접근 권한과 앱 종료 |
| 2 | [백엔드 프로세스 관리자](../src/main/supervisor.ts) | 실행 파일·Python 선택, 시작 확인, 상태 감시와 종료 |
| 3 | [화면의 호스트 어댑터](../src/renderer/services/hostAdapter.ts) · [API 클라이언트](../src/renderer/services/api.ts) | 브라우저·데스크톱 기능 차이와 요청 전달 |
| 4 | [학습 화면 상태](../src/renderer/stores/useTrainingStore.ts) | 작업 시작 응답, 진행·종료 이벤트와 프로젝트 전환 |
| 5 | [학습 API와 작업 관리자](../backend/api/routes_training.py) | 입력 검증, 작업 예약, 실행 조율과 조회 |
| 6 | [로컬 worker](../backend/engine/local_training_worker.py) · [원격 조정자](../backend/remote/coordinator.py) | 실제 실행의 소유권, 접속 복구와 결과 수신 |
| 7 | [학습 엔진](../backend/engine/trainer.py) · [작업 원장](../backend/engine/job_store.py) | 학습·재개 상태와 영속 작업 기록 |
| 8 | [플로우 화면](../src/renderer/components/flowchart/FlowchartStudio.tsx) · [플로우 엔진](../backend/engine/flowchart_engine.py) | 그래프 편집·검증, 노드 실행과 판정 집계 |

학습 흐름은 **화면 → 요청 검증·입력 출처 확인 → 원장·자원 예약 → worker → 학습 엔진 → 결과 기록 → 화면 조회**로 따라가면 됩니다. 원격 실행은 조정자가 입력·실행 환경을 준비하고, worker의 상태와 산출물을 확인하는 단계가 추가됩니다.

## 2. 혼동하기 쉬운 상태

| 개념 | 구분해야 하는 이유 |
| --- | --- |
| 작업 ID와 저장 모델 ID | 실행 상태를 찾는 ID와 평가·내보내기에서 모델을 찾는 ID의 계약이 다릅니다. 일부 전문 모델군은 변환 관계를 명시적으로 검사합니다. |
| 현재 프로젝트와 접수 당시 프로젝트 | 실행 중 화면을 바꾸더라도 결과는 접수 때 확인한 프로젝트에 등록해야 합니다. |
| 요청 세대와 실제 취소 | 오래된 응답을 화면에서 버리는 것만으로 실제 worker가 종료되지는 않습니다. |
| 취소 요청·worker 종료·예약 반환 | 각각 별도의 기록과 확인이 필요합니다. 연결 단절만으로 장치를 비었다고 판단하지 않습니다. |
| 원장 revision과 실행 fence | revision은 동시 상태 변경을, fence는 이전 실행 시도가 새 실행의 상태를 덮는 일을 막습니다. |
| warm-start와 exact resume | warm-start는 부모 가중치로 새 학습을 시작합니다. exact resume은 입력·설정·장치 등 호환 조건을 확인하고 저장된 학습 상태를 이어갑니다. |
| 원본 좌표와 중간 이미지 좌표 | ROI·resize·회전 후의 결과를 원본 좌표로 연결해야 측정과 후속 노드가 같은 위치를 가리킵니다. |

관련 계약은 [학습 입력 출처](../backend/engine/training_provenance.py), [학습 재개](../backend/engine/training_resume.py), [플로우 그래프 처리](../src/renderer/components/flowchart/flowchartGraph.ts)에 나뉘어 있습니다.

## 3. 리팩토링이 필요한 부분

### 우선 1: 학습 요청과 실행 조율 분리

`routes_training.py`는 HTTP 모델·응답, 입력 준비, 원장 연결, 로컬·원격 작업 관리와 복구를 함께 담당합니다. 특히 `_start_training()`은 재개 조건 검사부터 데이터 출처 고정과 worker 선택까지 처리합니다.

먼저 요청 준비를 부수 효과 없는 검증과 실제 입력 준비로 나누고, `TrainingLedgerLink`와 `TrainingJobManager`를 API 모듈 밖의 작업 서비스로 분리하는 것이 좋습니다. HTTP 상태·응답 형식, 예약 순서, 재시도 키와 기존 모듈을 사용하는 호출부의 호환성을 유지해야 합니다.

### 우선 2: 플로우 화면의 실행 제어 분리

`FlowchartStudio.tsx`에는 그래프 편집, 검증·실행 요청, 저장·재열기, 배포 전 근거 표시·다음 단계 이동과 UI 상태가 모여 있습니다. 응답 반영 여부는 프로젝트뿐 아니라 전송 문맥·그래프·요청 세대에도 의존합니다.

이미 분리된 `flowchartGraph.ts` 등의 순수 처리는 유지하고, 실행·검증의 상태와 응답 검사를 전용 hook으로 옮기는 순서가 적절합니다. 저장과 배포는 후속 단계로 나누고, 작업마다 필요한 식별자·검사 조건을 보존합니다. 연결선과 노드 종류별 속성 폼도 각각 분리할 수 있습니다.

`useTrainingStore.ts`는 복구·조회·실시간 이벤트에서 서버 상태를 화면 필드로 옮기는 처리가 반복됩니다. 공통 응답 정규화는 순수 함수로 추출하되, 각 경로의 기본값과 기존 상태 보존 규칙은 유지해야 합니다.

### 우선 3: 엔진의 준비·실행·결과 처리 분리

- `trainer.py`의 `train()`은 데이터·모델 준비, 재개 상태 복원, epoch 실행과 저장을 함께 처리합니다. 준비 결과를 명시적으로 전달하고 checkpoint 계약을 유지하는 작은 함수부터 분리할 수 있습니다.
- `flowchart_engine.py`의 `execute()`와 `_inspect_crops()`는 노드 실행, 좌표 변환과 판정 집계를 함께 다룹니다. 공통 좌표 변환과 결과 계약을 먼저 고정한 뒤 노드 실행기를 나누는 것이 좋습니다.

분리 과정에서 빈 검출의 의미, REVIEW 전파, 원본 좌표와 모델별 결과 필드를 바꾸면 기존 플로우의 판정이 달라질 수 있습니다.

### 후속: 원격 실행과 앱 생명주기 분리

원격 `run_remote_training()`의 입력·전송 묶음 준비와 `_monitor()`의 취소·상태 검증·결과 수신은 각각 독립된 책임입니다. `supervisor.ts`의 시작·종료 조율도 실행 파일 선택, 시작 확인과 프로세스 정리로 나눌 여지가 있습니다.

이 영역은 원격 재접속과 대상 OS의 프로세스 수명에 연결되므로, 앞선 분리 후 별도 변경으로 진행합니다. 실제로 소유한 프로세스만 종료하고, 종료를 확인하지 못한 작업의 예약을 유지하는 조건을 보존해야 합니다.

## 4. 변경 범위와 확인 방법

주석 추가는 실행 코드·문자열·API 계약을 바꾸지 않습니다. Python은 위치 정보를 제외한 AST 비교로, TypeScript·TSX는 기존 줄을 유지하고 코드 밖에 주석만 추가했는지 diff 검토로 확인할 수 있습니다.

실제 리팩토링은 위 항목을 하나씩 분리해서 진행합니다. 각 변경에서 시작·취소·재연결·프로젝트 전환·오래된 응답 처리처럼 해당 책임의 경계 조건을 기존 테스트와 대조합니다. 검사 명령과 격리 환경은 [기여 안내](../CONTRIBUTING.md)를 참고하세요. 자동 생성된 [API 타입](../src/renderer/services/generated/apiTypes.ts)은 직접 수정하지 않습니다.
