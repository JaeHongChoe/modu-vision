# 모두비전: 정보량을 줄이는 작업 공간 개편

## 상태와 범위

- 사용자 요청: 전체 디자인과 과도한 정보량 개선. 기능 전체를 리팩토링해도 되며 별도 브랜치에서 작업한다.
- 브랜치: `refactor/novice-workspace-20261114`.
- 기준 소스: `6fefa39a203a1c5b51f49130d36caeaefaa9064c` (PR #30의 통합 소스). 아직 main 병합이나 설치 앱 교체를 뜻하지 않는다.
- 현재 단계: 사용자가 두 번째 시안 묶음의 3번을 선택했다. 밝은 안내형 작업 공간을 구현 기준으로 고정한다. 이 문서만으로 제품 구현·검증 완료를 주장하지 않는다.
- 이번 설계는 앱과 localhost 웹의 공통 렌더러를 대상으로 한다. 모델 학습·저장·프로젝트 권한·배포 승인 정책은 유지한다.

## 의도

AI를 모르는 사람이 자기 사진으로 AI를 만들고, 결과를 이해하고, 검사에 사용하는 과정에서 지금 할 일을 찾을 수 있게 한다. 다양한 모델을 지원하는 기능 범위는 유지하되 화면이 모든 기능을 동시에 설명하지 않게 한다. '모두비전'을 사용자-facing 이름으로 일관되게 표시하되 번들 ID·앱 경로·저장소·마이그레이션 키는 별도 변경하지 않는다.

7±2는 단기기억에서 청크를 다루는 연구의 표현이며 모든 화면 요소를 일곱 개로 제한하는 UI 규칙으로 쓰지 않는다. 한 화면에서 주의를 요구하는 판단을 줄이고, 앞 화면의 내용을 기억하지 않아도 현재 선택과 상태를 확인할 수 있게 한다. 다음 수치는 제품 설계 휴리스틱이며 인간 대상 검증 결과가 아니다.

- 화면마다 명확한 현재 작업 하나와 주 행동 하나.
- 첫 화면의 핵심 정보는 약 3–5개 의미 묶음. 사진 목록이나 표의 행 수를 기계적으로 제한하지 않는다.
- 자주 쓰는 보조 행동은 1–2개를 가깝게 둔다. 필요에 따라 늘릴 때는 이유를 명시한다.
- 상세 설정·진단·이력은 이름이 명확한 진입점에서 접근한다.
- 막힌 이유, 저장 실패, 팀 잠금, 실행 중 작업과 중지/복구 행동은 접어서 숨기지 않는다.

근거: [Miller 1956](https://doi.org/10.1037/h0043158), [Cowan 2001](https://www.cambridge.org/core/journals/behavioral-and-brain-sciences/article/magical-number-4-in-shortterm-memory/44023F1147D4A1D44BDC0AD226838496). 이 연구에서 화면의 권장 요소 개수를 직접 도출하지 않는다.

## 현재 구조에서 확인한 원인

실행 중인 설치 앱의 데이터 준비 화면 한 곳은 직접 캡처했다. 이 화면은 개발 브랜치의 최신 실행본이 아니므로 소스 검토와 구분한다. 소스에서는 다음 중복이 확인된다.

- `App.tsx`가 전역 헤더, 학습 여정 안내, 단계별 화면, 하단 안내, 도우미를 동시에 배치한다.
- `WizardHeader`의 네 목표·하위 단계, `LearningJourneyPanel`, `OperatorGuidanceBanner`, `WizardFooter`가 위치와 다음 행동을 반복해서 안내한다.
- `DatasetStudio`는 추가 메뉴·집중 보기·관리 도구·통계·준비 상태를 각각 노출한다.
- `TrainingController`의 simple/full 고급 설정, `EvaluationStudio`의 비교 컨트롤은 표시 위치 때문에 중복된 구성요소를 갖는다.
- 기존 studio 색상과 workspace 색상이 공존한다. 공통 구성요소는 같은 토큰 체계로 묶되 이미지 캔버스의 명도는 독립적으로 유지한다.

## 접근 방식

1. 색상·여백만 보완: 비용은 작지만 중복 안내와 정보 구조를 그대로 남기므로 목표에 불충분하다.
2. 공통 화면 틀과 단계별 정보 계층을 먼저 정의하고 순차 이관: 기존 상태·저장 계약을 유지하며 전체 인상을 바꿀 수 있다. **권장 구현 방식**이다.
3. 새 앱을 처음부터 작성: 시각적 자유도는 크지만 축적된 프로젝트·라벨·작업 실행 계약을 재구현해야 하므로 이번 범위에서 선택하지 않는다.

사용자는 전체 리팩토링과 브랜치 작업을 허가했다. 위 구현 방식 2와 다음 세 시각 후보의 구체적 배치는 Codex 제안이다. 시각 선택을 별도로 기록한다.

## 세 시각 방향의 공통 조건

데이터를 가져온 동일 상태로 비교한다: 예제 표면 검사, 사진 64장, OK 32/NG 32, 시험 사진 12장. 합성 이미지 목업이며 실제 모델 결과·품질·배포 승인 근거가 아니다.

- 차분한 프로젝트 작업실: 밝은 중성 배경, 왼쪽의 짧은 작업 탐색, 넓은 사진 목록, 헤더의 단일 다음 행동.
- 사진 중심 작업대: 어두운 중성 캔버스, 큰 선택 사진과 필름스트립, 현재 사진의 설정과 행동을 한 곳에 둔다.
- 첫 사용 안내 공간: 현재 할 일 하나와 확인할 사진을 중심으로, 짧은 진행 맥락과 다음 행동을 제공한다.

색상 후보만 다른 화면을 만들지 않는다. 목록 중심·선택 사진 중심·안내 중심의 정보 배치가 실제로 달라야 한다. 최종 선택 후 사진 준비·학습·결과 화면에 같은 규칙을 적용한 뒤 나머지 단계로 확장한다. 모델 생성 이미지의 임의 문구·아이콘은 구현 계약이 아니며 이 문서의 실제 동작과 문구 기준으로 교정한다.

## 공통 화면 틀

`App`의 프로젝트/컴퓨트 구독과 작업 생명주기는 유지하고 렌더링만 분리한다.

1. 작은 프로젝트·유틸리티 영역: 프로젝트, 작업 상태, 도우미, 설정. 상시 PID·포트·드라이버 정보를 제거하고 기술 상세에서 접근한다.
2. 하나의 작업 탐색: 사진 준비 → AI 만들기 → 결과 확인 → 검사 사용. 기존 1–6 단계와 연결되며 저장 ID나 도우미 `open_step` 계약을 바꾸지 않는다.
3. 하나의 화면 제목과 간단한 상황 설명. 전역 제목·단계 제목·별도 안내 배너를 겹치지 않는다.
4. 주 작업 영역: 사진/캔버스/결과/실제 진행 상태.
5. 하나의 문맥·행동 영역: 현재 선택, 가장 먼저 필요한 조건, 주 행동. 상단과 하단에 동일 CTA를 중복하지 않는다.

도우미는 닫거나 펼칠 수 있으며 닫아도 실행 중 계획을 취소하지 않는다. 좁은 창에서 패널이 작업 캔버스를 눌러 사용할 수 없게 만들지 않는다. 자동 진행과 작업 센터는 기능을 유지하되, 설정 진입점과 실행 중 상태 표시를 구분한다. 기본 테마를 바꾸더라도 기존 사용자의 명시적 테마 설정을 덮어쓰지 않는다.

목록이 상세 영역으로 이동해도 모든 기능에는 이름으로 찾을 수 있는 경로가 있어야 한다. 기존 deep-link/복구 타깃은 해당 영역을 열고 포커스를 보낸다. 내보내기·백업·서버·설정·계정·도우미 연결도 기능 보존 목록에 포함한다.

## 모델을 고르는 흐름

`ModelFamilyCatalog`와 capability API를 단일 출처로 유지한다. classification, segmentation, detection, anomaly, patch_classification, ocr, rotated_detection, defect_gan, enhancement, rotation의 접근·선택·별도 작업대를 모두 보존한다.

초보자에게는 원하는 결과 예시와 목적을 먼저 보여주고, 선택 후 필요한 모델·데이터·장치 상태를 설명한다. 모델을 자동으로 다른 계열로 바꾸거나 생성 전용 기능을 학습/평가 완료로 표현하지 않는다. 사용할 수 없는 항목도 이유와 가능한 다음 행동을 보여준다.

## 동작 보존 계약

- 탐색은 기존 `useProjectStore.setStep`을 사용한다. 새 UI에 단계/프로젝트 상태 복사본을 만들지 않는다. 단계 이동과 학습·평가·저장·검사 실행은 별도 행동이다. 기존 footer의 안내 버튼을 실행 버튼으로 몰래 바꾸지 않는다.
- `saveOpenEdits`의 백엔드 프로젝트 재결합, source 보존, 흐름 초안 선저장, 라벨 저장 실패 차단을 유지한다. 새 레이아웃으로 옮길 때 미저장 편집을 버리는 unmount를 만들지 않는다.
- 프로젝트·작업 종류·컴퓨트 변경의 busy guard, revision/transport scope, stale response 거절과 selection custody를 유지한다.
- `workflowReadiness`의 ready/blocked/checking/unknown과 `stepProgress`의 근거를 유지한다. 초안/채택, 평가 실행/성능, 작업 완료/현장 승인 상태를 합치지 않는다.
- 가장 먼저 필요한 조건 하나를 주 행동 가까이 보여주되 전체 조건은 열람 가능하게 한다. 저장 실패·팀 잠금·연결 불확실·실행 중·일시정지·사람 입력 필요를 서로 다르게 표현한다.
- 도우미 닫기는 표시만 변경한다. 확정된 쓰기 작업은 결과를 기록하고, 프로젝트/수신자 변경을 기존대로 잠근다. 이미지 전송·권한·유료/실계정 동작 동의와 정책은 유지한다.
- 자동 진행 대화상자를 닫아도 이미 시작된 작업의 소유권과 상태를 유지한다. 재렌더링이나 패널 열기로 실행을 중복 시작하지 않는다.
- 모달 포커스 가두기/복원, Escape, 입력 중 단계 단축키 차단, 그래프·다각형 편집 단축키, scoped error와 복구 타깃을 유지한다.

## 시각·문구·접근성 기준

- 기존 Pretendard 기반 한글 읽기성을 유지한다. 본문 14–16px 수준을 기준으로 제목·설명·보조 정보의 차이를 명확히 한다.
- 카드/테두리 대신 먼저 간격·정렬·글자 크기로 구분한다. 상태 색에는 텍스트를 동반한다.
- 기본/호버/포커스/선택/비활성 상태를 공통 토큰과 구성요소에서 관리한다. light/dark 모두 지원하며 이미지 판독 영역의 대비를 따로 검토한다.
- 경고는 무엇이 막혔는지와 해결 행동을 먼저 쓴다. 상세 원인·기록은 펼쳐 본다. 오류를 단순히 접거나 성공으로 바꾸지 않는다.
- 한국어·영어의 구조가 같게 한다. 작은 창에서는 탐색이 축약되고 문맥 패널은 접근 가능한 서랍으로 바뀌며, 핵심 작업과 오류·중지 버튼은 잘리지 않는다.
- 데이터 없음·로딩·부분 실패·오프라인·진행 중·완료·복원 상태를 기본 화면과 같은 수준으로 설계한다.

## 구현 순서와 검증

1. 시각 방향 선택을 기록하고 상세 구현 계획 작성. 화면/상태/기능 경로 목록을 고정한다.
2. UI 전용 공통 shell·탐색·stage header·문맥 영역을 추출한다. 상태 효과와 실행 핸들러는 기존 소유자에 둔다.
3. 중복 안내/진행 표시/CTA를 통합한다. 기존 키보드·복구 타깃 계약을 유지한다.
4. 데이터→학습→평가→검사를 이관하고, 캔버스 높이와 편집 상태 민감도가 높은 라벨·그래프 편집은 마지막에 이관한다. simple/full 중복 JSX를 공통 구성요소로 정리한다.
5. 모든 계열과 보조 기능의 접근 경로를 대조한다. README·초보자 안내와 실제 화면을 함께 갱신한다.
