# 모두비전 작업 중심 사용 흐름 개선

## 목적과 범위

AI 비전문가가 사진의 정답을 고르고, 학습 결과에서 문제 사진을 찾고, 저장한 모델·검사 흐름의 사용 맥락을 이해하도록 기존 기능을 정리한다. 사용자가 이미 선택한 녹색 novice 작업 화면, 네 가지 목표와 여섯 내부 단계, Supervisely식 학습 전 준비 작업대의 연속 개선이다. 이번 요청은 구현을 맡긴 요청이며, 새 브랜드나 데이터/실행 정책을 선택하는 작업으로 확대하지 않는다.

기준 소스는 main `8f1b6051af64774b8f2f00b63cf9eabbaf26a36c`. 기능 브랜치 `feat/product-workflow-polish-20261116`에서 진행한다. 실행 중인 설치 앱·8443 서버와 사용자의 자료는 교체하거나 수정하지 않는다.

## 현재 관찰

현재 설치 앱에서 소유 합성 프로젝트64장의 사진 준비·라벨링·학습·평가·검사 준비·검사 사용을 읽기/화면 이동으로 확인했다. 여섯 화면은 `.superpowers/sdd/2026-11-16-product-completion/audit/`에 저장하고 열어 확인했다. 학습·평가·검사를 새로 실행하지 않았다. 기존 프로필의 기술 상세/안내 펼침 상태를 관찰했으며 이를 최초 실행 기본값이라고 주장하지 않는다.

- 분류 화면에서 사진 클래스와 선택적 영역 라벨이 함께 나오고, 일곱 형상 도구가 두 줄로 노출된다. 영역이 없어도 사진 분류 정답이 있을 수 있는데 빈 객체 목록은 ‘라벨 없음’으로 시작한다.
- 결과 화면은 원시 task/job ID, ‘코호트’, 상태 코드를 주요 선택지에 사용한다. 통계 영역·이미지 목록·원본/결과 비교가 작은 화면 폭을 나누어 쓰며, 결과 숫자는 관련 사진을 여는 자연스러운 진입점이 아니다.
- 검사 사용은 저장 흐름 이름·선택 모델·실행 위치와 함께 긴 graph SHA와 job ID를 먼저 보여준다. 근거는 보존하되 이를 읽어야 검사 맥락을 이해하는 구조를 바꾼다.
- 오른쪽 다음 행동 상세에도 긴 식별자가 들어간다. 준비도와 실행/오류/취소 상태의 의미는 유지해야 한다.

## 접근 방식

1. **선택한 방식: 기존 엔진 위의 작업 중심 UI.** CVAT/Label Studio의 문맥 도구, Roboflow/FiftyOne의 오류 사진 탐색, Supervisely/MLflow의 기록 연결 패턴을 기존 store/API/기록에 구현한다. 별도 서비스나 큰 의존성을 추가하지 않는다.
2. 대형 도구의 전체 UI·DB·서버를 내장하면 현재 프로젝트/라벨셋/저장 기록과 중복된다. 기존 저장·복원·작업 가드의 교체 비용이 커 이번 묶음에 넣지 않는다.
3. 고급 그래프 렌더러 교체는 별도 후속으로 둔다. 선형 학습 준비 작업대와 현재 저장 graph 계약에 새 그래프 라이브러리가 필수는 아니다.

공개 문서·화면의 관찰과 OSS 소스 이식은 구분한다. n8n 코드는 제품 내재화에 복사하지 않는다. 개별 OSS 파일을 실제 이식한다면 정확한 commit/license/notice/provenance를 별도로 기록한다. 이번 묶음은 공개 UX에서 배운 동작의 독립 구현이다.

## 구현 1: 작업에 맞는 라벨 도구

- 기존 `VisionTask`, `viewMode`, `useAnnotationStore`를 그대로 사용한다.
- 간단히 보기에서는 작업에 맞는 도구를 먼저 제시한다. 분류는 사진 클래스가 정답임을 먼저 설명하고 선택적 영역 도구를 구분한다. 검출은 박스, 회전 검출은 회전 박스, 분할은 다각형/브러시/지우개/자동 선택을 우선한다. 나머지는 접을 수 있는 ‘다른 영역 도구’에서 접근한다.
- 모든 기존 도구와 단축키를 유지한다. 현재 선택된 도구는 접힌 영역에 숨지 않는다. 전환·렌더·접기만으로 activeTool, 형상, 클래스, 마스크, 저장 상태를 바꾸지 않는다. 전체 보기의 도구 접근은 유지한다.
- 분류에서 영역 객체가0개인 상태는 사진 분류 정답 부재와 같지 않다. 빈 객체 목록을 ‘선택적으로 그린 영역 없음’으로 설명한다. 실제 클래스 값의 판정은 기존 `ClassificationClassPicker`가 소유하며 새 추정/자동 채택을 만들지 않는다.
- 도구막대·원본 이미지·저장/실행취소·오류는 캔버스 위에서 안정적으로 접근 가능해야 한다. 집중 보기, 좌표/viewport, point editing, edit lease, save-before-leave는 유지한다.

## 구현 2: 결과에서 사진으로 이어지는 평가

- 모델 선택은 작업 종류의 한국어 이름과 구분 가능한 읽기 쉬운 번호/완료 시각을 먼저 보여준다. 정확한 job ID는 기술 근거에서 계속 확인한다. 데이터 버전도 이름·장수·읽기 쉬운 상태를 사용한다. 값/키는 원래 ID를 유지한다.
- 사용자에게 ‘시험 이미지 묶음’이라는 말을 사용한다. 이미 있는 평가 실행 handler, target/device, source/revision 가드는 바꾸지 않는다.
- 결과 요약에서 관련 오류 사진 목록으로 이동할 수 있게 한다. 현재 `sampleFilter`, 선택 이미지, saved threshold/preview 구분과 기존 라벨 수정 이동 경로를 재사용한다. 클릭은 화면/필터만 바꾸며 평가나 라벨 저장을 새로 실행하지 않는다.
- 간단히 보기에서 결과·이미지 비교에 공간을 우선 배정하고 고급 통계/기술 근거를 접어 접근한다. 컴포넌트·작업 상태를 접기 때문에 초기화하거나 숨겨진 mutation을 실행하지 않는다.
- 원격 실행 중/취소 요청/ACK/worker 종료의 구분, 실행 오류와 복구 동작은 항상 보인다. 긴 ID/hash/전체 근거만 펼침 영역에 배치한다.
- 이미지 단위 미검/과검, 검출 객체 단위·분할 픽셀 단위 지표, 지원하지 않는 전문 모델을 혼동하지 않는다. 지원 모델·임계값 조정 가능 여부를 새 UI 때문에 확장하지 않는다. 미검이 있는 결과를 양호하게 표시하거나 준비도/승인 조건을 바꾸지 않는다.

## 구현 3: 검사와 다음 행동의 읽기 쉬운 맥락

- `SavedFlowIdentityCard`와 `BatchInspectionPanel`에서 저장 흐름 이름, 연결 모델 수, 현재 선택과 저장된 실행 근거의 구분을 먼저 보여준다. 전체 version/graph SHA/model job ID는 같은 데이터의 ‘실행 근거’에 보존한다.
- 저장 흐름의 missing/loading/error 상태, 실제 실행 시작 시 검증한 snapshot과 ‘다음 실행에 사용할 현재 선택’을 구분한다. 최근 성공한 검사 이력을 현재 선택의 검증으로 대체하지 않는다.
- `WizardFooter`의 오른쪽 주 행동과 권한/준비도 소유권은 유지한다. 펼친 상세 안에서 긴 식별자 근거와 설명을 정리해도 현재 오류와 다음 행동을 가리지 않는다. 같은 단계 안의 전처리 설정 이동을 전체 준비 완료나 학습 실행으로 오인시키지 않는다.

## 공통 시각/행동 계약

- 기존 `DESIGN.md`, `UX-CONTRACT.md`, `design-tokens.css`, `novice-workspace.css`, 생성형 light theme를 따른다. 새 브랜드·폰트·색 체계를 추가하지 않는다.
- native button/select/details와 기존 workspace 버튼/레코드/상태 의미를 재사용한다. 클릭 가능한 숫자는 실제 button이고 이름·현재 선택·키보드 포커스를 제공한다.
- 긴 한글/이름, 720px 화면, assistant sidebar가 열린 폭, 양 테마, loading/empty/error/stale/context 전환을 검증한다. 접힌 선택지의 활성 도구와 에러는 발견 가능해야 한다.
- 원본/라벨/labelset/source fingerprint/held-out 평가/모델/승인/저장 버전/작업 종료의 기존 의미를 유지한다. 임의 Python/CLI/모델 실행, GPT 호출·이미지 전송·보안 권한 변경을 추가하지 않는다.

## 검증과 납품

행동 변화에 필요한 회귀를 먼저 실패시켜 확인하고 구현한다. renderer/main 전체, 타입/E2E 타입, light theme, 서비스/행동 근거 검사와 관련된 실제 분리 browser 흐름을 실행한다. 독립 코드 검토를 받는다. 기존 실패 기록과 미검증 경계는 보존한다.

사용자에게 현재 구현 범위/제약, 이번 변경, 참고 원천, 실제 검증과 남은 후속을 분리해 보고한다. 기능 브랜치/PR을 만들고 CI는 정확한 최종 head 기준으로 확인한다. 현재 실행본 교체·새로운 배포는 이 UI 구현 검증과 구분한다.
