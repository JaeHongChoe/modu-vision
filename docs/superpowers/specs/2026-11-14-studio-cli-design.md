# 모두비전 공통 CLI와 GPT 기능 탐색

## Intent
Expose the installed product's authenticated HTTP operations through one machine-readable CLI, and connect the same operation descriptions to the built-in GPT. The existing task executor continues to perform supported app writes. Project roles, current context, job ledgers, model evidence and native-host consent remain authoritative.

## Approach and decisions
A second headless implementation of every engine would drift from the app. A shell-execution tool would neither describe product contracts nor keep the app's state coherent. Use a live, authenticated operation catalog derived from the registered FastAPI OpenAPI document, a standard-library HTTP CLI, and a small lazy-discovery GPT adapter. This is the implementation choice made for the user's request to apply CLI across functions. It needs no new runtime dependency.

## Catalog contract
`GET /api/automation/catalog` is metadata only, authenticated but available before project selection. Only this exact GET bypasses project/storage selection; all real operations retain existing middleware. It describes every registered HTTP `/api/` and `/health` operation, including dynamically installed local-host routes. `schema=StudioOperations/v1`; operation `id` is `METHOD /path`; fields: method,path,group,summary,transport,effect,assistant,input(parameters/request_body),responses. Parameters: group,operation,offset (>=0),limit (1..1000),schemas (bool). Lists contain compact metadata; an operation detail includes its OpenAPI parameters/requestBody/responses and transitively referenced components under components.schemas. Include group counts,total,next_offset,server_version. Unknown group/operation yields 404. Never infer read-only from GET: evaluation/calibration endpoints may execute. Unknown operations default to effect execute and assistant manual. Maintain an exact safe observation allowlist; task-capable operations identify an existing task action but never grant permission. Catalog data contains schemas, not account/project values or secret instances.

## CLI contract
`python -m backend.studio_cli` imports only Python standard library. `capabilities` and `describe OPERATION` read the live catalog; `call OPERATION` constructs a request exclusively from its catalog detail; `diagnostics` requires explicit project/context and aggregates named safe observation operations with per-section failures; it never reads project/current because that endpoint can initialize a default project. `--url`/`MODU_STUDIO_URL` identify an explicit http loopback or HTTPS server. TLS verifies by default; `--ca-file` trusts an explicit CA and there is no insecure option. Credentials come from `VISION_AI_STUDIO_API_TOKEN` (desktop) or `MODU_STUDIO_BEARER_TOKEN` (account). Explicit project/context travel in X-Vision-Project/X-Vision-Context. Credentials and connection headers never appear in stdout/errors. No account profiles or auth files are discovered/read. No implicit login, shell or helper invocation. Explicit login uses hidden terminal input or --password-stdin and creates a new owner-only origin-bound --session-file; existing app credential stores are never discovered. A session file cannot be mixed with environment credentials.

Calls accept --path-json, --query-json, --body-json/--body-file, raw --upload-file and multipart --file FIELD=PATH/--form-json, plus --output for binary. Server validates business schemas. Client rejects missing/unknown path and query parameters, duplicate/nonfinite JSON, invalid path traversal (multi-segment values only for actual registered path converters), arbitrary headers/URLs, conflicting body encodings. All requests are single-attempt; redirects are refused. Timeouts after dispatch have an unconfirmed outcome and never trigger retries. Accepted jobs are not completed work. JSON results preserve structured HTTP detail and X-Vision-Context; binary files stream to an owned sibling temporary file, verify any server SHA256, then publish without overwriting existing output. One bounded JSON envelope goes to stdout, CLI usage errors are JSON too; nonzero status distinguishes argument/transport/HTTP/unconfirmed errors.

## GPT integration
Add lazy list/detail and safe-observation tools using the same catalog. Keep <=40 tools and <=24000 schema chars. Do not let a provider choose an arbitrary URL/method/path/header, read account secrets, or label an executable GET as read. Observation uses an exact client/server matching allowlist and rechecks project generation and transport before/after. Output is bounded, redacted, declares truncation/partial results, and never returns credentials. Existing task-action mappings point GPT to propose_task, its immutable plan and existing executor; no raw API write bypass or new automatic truth/approval/deployment authority is introduced. Distinguish discoverable CLI operations from GPT-permitted actions in every response.

## Coverage and boundaries
Projects/data/annotations/masks/drafts/training/evaluation/flows/inference/exports/remote/job/account administration HTTP operations all become discoverable/callable using their current server policy. Native operations are listed only when installed and keep cookie/Origin/CSRF/tab/consent checks; a bearer CLI cannot impersonate a browser tab. CLI supplies explicit inputs rather than manipulating unsaved renderer controls. Screen navigation, OS picker permission and unmounted renderer actions are not claimed to be independent headless functions. This extension does not itself improve model accuracy, run a paid provider, replace app/web installations, merge or deploy.
