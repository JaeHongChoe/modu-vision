# 기능 점검 수정 (2026-10-20)

2026-10-20 기능 점검에서 나온 문제(F-01~F-22), 개선 제안(A1~A7), 선택 추가(B1~B5)를 모두 구현·검증 대상으로 진행한 기록입니다. 같은 원인의 항목은 한 번에 고쳤습니다. 검증 칸의 "백엔드"는 pytest, "화면 단위"는 렌더러 회귀 테스트, "브라우저"·"Electron"은 Playwright 스펙, "실사용"은 임시 작업 공간에서 앱을 직접 조작한 결과입니다.

## 실사용 전체 경로 (2026-10-21, 임시 작업 공간)

합성 분류 데이터(정상 40장, 불량 40장, 손상 파일 1장)로 앱을 직접 조작했습니다. 원본 데이터와 다른 프로젝트는 건드리지 않았고, 시험용으로 넣었던 이미지는 지우지 않고 임시 보관 폴더로 옮겼습니다.

1. 빈 프로젝트 → 가져오기: 손상 파일 1장이 사용 안 함으로 빠지고 학습 가능 80장, 분할 "자동 · 저장 안 됨"과 차단 안내.
2. 2단계에서 `ng_00.png`의 클래스를 OK로 지정: 파일은 NG 폴더에 그대로, 1단계 수가 NG 39 · OK 41로 바뀜.
3. 60/20/20 분할 저장: "저장됨", 48/16/16, 시험 16장 경고, 현장 조건 1/5.
4. 3단계: 카드가 "이 컴퓨터 · MPS (자동 선택)", 준비 검사가 스스로 실행. CPU로 8회 학습을 3회째에 중단 → 목록에 바로 "Epoch 5/8 완료" → 이어서 6~8회만 학습하고 완료.
5. 4단계: "정확도 100% · 실제는 81~100% 사이일 수 있음 (시험 16장)", 추천 점수 0.70 적용.
6. 5단계: 모델 노드에 "평가(4단계)에서 정한 기준 점수 0.70"과 "이 값 쓰기" → 저장 버전 → 시험 코호트 고정 → 라벨을 정답으로 확정(16장) → 흐름 평가 미검 0 · 과검 0.
7. 6단계: 일괄 검사 16/16, CSV에 결함 점수·검사 시각·장치·지연 시간, 단일 모델 내보내기에 "아직 승인하지 않은 모델" 안내.
8. 데이터 변경: 이미지 1장을 더하자 하단 안내가 "학습한 뒤 데이터가 바뀌었습니다: 이미지 추가 1장 (OK/ok_added.png)"와 "다시 학습"만 제시, 6단계 검사 거절도 같은 원인을 말함. 이미지를 보관 폴더로 옮겨 되돌린 뒤 클래스만 바꾸자 "이미지 클래스 지정 바뀜"과 "학습 때 버전으로 되돌리기"가 나오고, 1단계 데이터 버전이 그 버전을 표시한 채 열림 → 확인 후 복원(자동 백업) → 모델·평가가 다시 현재.
9. 재시작: 프로젝트와 1~4단계 완료 표시가 돌아오고, 라벨 변경으로 무효가 된 흐름 평가 때문에 5단계는 완료로 남지 않음.
10. 실패 경로: 검출 프로젝트에 클래스 폴더 → 기대 구조 안내, 없는 폴더 → "폴더를 찾을 수 없습니다", 클래스 하나 → 1단계·3단계 차단과 서버 거절 문구.

이 과정에서 찾아 고친 것: 1단계 클래스 수가 제외된 손상 파일을 셈(통계 응답), 클래스 편집으로 선택 모델이 비면 데이터 변경 안내가 일반 문구로 바뀜, 3단계가 한 클래스·저장 안 된 분할을 안내만 하고 시작 버튼은 열어 둠.

## 가중치가 필요한 스펙 (`@owned-model`)

호스팅 CI는 `--grep-invert @owned-model`로 이 스펙을 빼므로 자동으로 확인되지 않습니다. 이 컴퓨터의 캐시된 공식 가중치(DINOv3 ViT-S/16 safetensors, YOLO26n, YOLO26n-OBB)를 `MV_E2E_DINO_WEIGHTS`, `MV_E2E_YOLO_WEIGHTS`, `MV_E2E_OBB_WEIGHTS`로 지정해 로컬에서 돌립니다. 없는 가중치나 바인딩은 꾸미지 않습니다(GAN용 EfficientNet-B0, 보존 모델 바인딩 파일은 이 컴퓨터에 없음).

| 스펙 | 결과 |
| --- | --- |
| DINOv3 분류·분할, YOLO 검출, YOLO OBB, 이상 탐지 3방식 보정 | 통과(CPU 실제 학습 포함) |
| `core-model-target` | `MV_E2E_GAN_CLASSIFIER_WEIGHTS`(EfficientNet-B0)가 없어 실패. 환경 |
| `retained-studio-*` | 보존 모델 바인딩 파일이 없어 실행 불가. 환경 |

## Electron (격리 프로필)

- 통과 13/13: 분류 요약, 라벨 편집 보존 2개, 저장 평가 선택, 현장 프로토콜(실제 소켓 ACK), F064 흐름 3개, OCR 2개, 검수 대기열.
- `flow-model-less-reopen-controls`(Electron): 401은 해결되었습니다. 이후 시간 초과의 원인을 계측으로 구분했습니다. 실패한 요청은 네트워크에서 약 15 ms 만에 끝났고(`responseEnd` 14.6 ms), Playwright가 Electron의 DevTools 프로토콜로 본문을 테스트에 넘기는 데 1~12.5초가 걸렸습니다. 즉 앱의 지연이 아니라 검사 장치의 지연입니다. 스펙은 이제 앱의 응답 완료(`response.finished()`)를 기존 10초 창으로 보고, 본문 전달에는 별도 여유를 줍니다. 테스트 예산은 브라우저 240초(로컬 114초, 호스팅 러너에서 160초 초과), Electron 660초입니다(480초 예산으로 모든 검사를 통과한 실행이 8.3분). 검사 항목은 그대로이며, 이 스펙은 이제 Electron에서도 통과합니다.

## 15차에서 넘어온 회귀

15차의 한국어 노드 카드 때문에 `service-s0-05`·`service-s0-08`이 노드를 'threshold'·'rule:' 글자로 찾지 못하고, 카드와 속성 패널이 둘 다 '8.00'을 보여 정확 일치가 두 번 되었습니다. 앞의 것은 CI 브라우저 스펙입니다. 둘 다 고쳐 11/11 통과합니다.

이전 커밋 4364175의 호스팅 CI에서 실패한 브라우저 스펙 13개를 지금 head에서 다시 돌리면 11개는 통과합니다. `browser-team-session`은 main에서도 실패합니다(#7). `saved-queue-remaining-controls`는 main에서는 통과하고 이 브랜치에서 실패했습니다. 15차부터 4단계가 평가 결과가 도착할 때 근거를 다시 읽으면서 `model_deployments.sqlite3`를 읽기 전용으로 엽니다. 이때 WAL 모드의 SQLite가 `-shm` 색인 파일의 시각을 바꾸고(내용은 같음), 그 시각이 스펙의 쓰기 없음 확인에 걸렸습니다. 그 파일은 목록에는 남기고 바이트·시각은 고정하지 않게 고쳤습니다.

## 환경 때문에 남은 것

- 원격 GPU 학습, 실제 다중 사용자 서버 운영, Windows 설치·실행, macOS 자동 시작, 현장 장비(PLC·MES) 실장비: 승인된 장비·접속이 필요합니다.

## 호스팅 CI 시간 예산

`source` 작업의 CPU 회귀 단계가 호스팅 러너에서 50~71분(실행 39396577197, 39381902182, 39398496681, 39407506214), 준비 약 3.5분과 마지막 결함 기준 단계 약 2.7분을 더하면 최대 약 77분이 걸려 75분 제한이 회귀 단계 통과 뒤 마지막 단계를 취소했습니다. `browser` 작업은 48~69분이었습니다. 테스트를 빼거나 나누지 않고 제한을 `source` 110분, `browser` 100분(측정 최댓값의 약 1.4배)으로 바꾸고, 이 값을 고정하는 `test_source_ci_model_lanes.py`도 함께 갱신했습니다.
