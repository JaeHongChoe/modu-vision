# 기능 점검 수정 (2026-10-20)

2026-10-20 기능 점검에서 나온 문제(F-01~F-22), 개선 제안(A1~A7), 선택 추가(B1~B5)를 모두 구현·검증 대상으로 진행한 기록입니다. 같은 원인의 항목은 한 번에 고쳤습니다. 검증 칸의 "백엔드"는 pytest, "화면 단위"는 렌더러 회귀 테스트, "브라우저"·"Electron"은 Playwright 스펙입니다. "실사용"은 임시 작업 공간에서 브라우저 모드 앱을 직접 조작한 결과입니다(Electron 앱 아님). "직접 확인"은 새 임시 사용자 데이터 폴더에서 API를 직접 불러 본 결과입니다.

사용자 원본 이미지·라벨·클래스 이름·모델·저장된 프로젝트와 흐름은 바꾸지 않습니다. 분류 클래스 지정은 파일을 옮기지 않고 프로젝트 쪽에 기록합니다. 바뀐 라벨·분할·클래스는 데이터 버전과 오래된 근거 판단에 그대로 반영됩니다. 승인된 모델·흐름의 판정 점수는 저절로 바뀌지 않습니다.

## 실사용 전체 경로 (2026-10-21, 임시 작업 공간, 브라우저 모드)

합성 분류 데이터(정상 40장, 불량 40장, 손상 파일 1장)로 앱을 직접 조작했습니다. e2e 하네스로 격리된 백엔드와 빌드한 화면을 띄우고 브라우저에서 열었습니다. Electron 앱은 조작하지 않았습니다. 하네스 페이지 서버는 화면을 '모두 보기'로 엽니다(ffa0745). 원본 데이터와 다른 프로젝트는 건드리지 않았습니다. 시험용으로 넣었던 이미지는 지우지 않고 임시 보관 폴더로 옮겼습니다.

1. 빈 프로젝트 → 가져오기: 손상 파일 1장이 사용 안 함으로 빠지고 학습 가능 80장, 분할 "자동 · 저장 안 됨"과 차단 안내.
2. 2단계에서 `ng_00.png`의 클래스를 OK로 지정: 파일은 NG 폴더에 그대로, 1단계 수가 NG 39 · OK 41로 바뀜.
3. 60/20/20 분할 저장: "저장됨", 48/16/16, 시험 16장 경고, 현장 조건 1/5.
4. 3단계: 카드가 "이 컴퓨터 · MPS (자동 선택)", 준비 검사가 스스로 실행. CPU로 8회 학습을 3회째에 중단 → 목록에 바로 "Epoch 5/8 완료" → 이어서 6~8회만 학습하고 완료.
5. 4단계: "정확도 100% · 실제는 81~100% 사이일 수 있음 (시험 16장)", 추천 점수 0.70 적용.

7. 6단계: 일괄 검사 16/16, CSV에 결함 점수·검사 시각·장치·지연 시간, 단일 모델 내보내기에 "아직 승인하지 않은 모델" 안내.

## F-03 클래스당 장수 측정 (2026-10-21)

## CI 운용: 빠른 검사와 병합 전 전체 회귀 (2026-10-22)

전체 회귀(`ci.yml`)가 PR 커밋마다 돌면서 한 브랜치의 실행이 한 줄로 쌓였습니다(`queue: max`). #410 실측으로 `source`는 56분(pytest 51분), `browser`는 45분(Playwright 42분)이었고, 커밋 다섯 개면 다섯 시간 넘게 기다렸습니다. 정적 검사(범위·증거 게이트, 타입, 렌더러 회귀, 빌드)는 준비를 포함해 약 3분입니다.

- 전체 회귀의 작업 정의(테스트 목록, 단언, 시간 예산, 대기열, 영수증)는 한 글자도 바꾸지 않았습니다. 트리거에서 `pull_request`만 빼고, 수동 실행과 main 푸시를 남겼습니다.
- 빠른 검사(`ci-fast.yml`)는 PR 커밋마다 별도 대기열에서 돕니다. 같은 브랜치의 이전 실행은 새 커밋이 오면 멈춥니다. 병렬 작업은 다음과 같습니다.
  - 정적 검사: 전체 회귀와 같은 명령입니다.
  - 관련 pytest(6개로 나눔)와 관련 화면 스펙(4개로 나눔): 고르는 범위는 전체 회귀 목록 안뿐입니다.
- "바뀐 것"은 이 브랜치에서 빠른 검사가 마지막으로 통과한 커밋부터 셉니다. 취소되거나 실패한 실행은 기준점이 되지 않으므로 그 변경은 다음 실행이 다시 고릅니다.
- 병합 게이트("Merge readiness", `ci-merge-gate.yml`): 그 커밋에서 전체 회귀가 성공했을 때만 통과합니다.
  - 빠른 검사와 다른 워크플로에 둡니다. 같은 워크플로에 두면 게이트가 실패하는 동안 빠른 검사 실행 전체가 실패로 남습니다. 그러면 기준점이 앞으로 나아가지 않아, 매 커밋마다 main부터의 큰 범위를 다시 고르게 됩니다(검토에서 지적).
- 선택 예: 스펙 하나를 고친 커밋은 CI 구조 테스트 3개와 그 스펙 하나를 고릅니다. `local_training_worker.py`만 바뀌면 pytest 303개 가운데 15개를 고릅니다. 이 브랜치 전체(main 대비 349개 파일)는 pytest 165개와 스펙 84개입니다. 그래서 첫 빠른 실행만 크고, 다음부터는 그 이후의 변경만 고릅니다.
- 첫 실측(cd03b0d, 실행 39710076633): 처음이라 main과 갈라진 지점(a267a4c)부터의 353개 파일을 골랐고, 11개 작업이 모두 통과했습니다. 걸린 시간은 13.25분이었습니다(전체 회귀는 직렬로 약 56분). 작업별 시간은 다음과 같습니다.
  - 정적 검사: 2.6분
  - pytest 6개: 4.5~13.2분
  - 화면 4개: 5.7~12.8분(32+32+37+…개 통과)
  - 같은 커밋의 병합 게이트는 "Full regression has not run on cd03b0d…"로 실패했습니다(의도한 동작).
- 병합 조건: 마지막 커밋에서 빠른 검사가 모두 통과하고, 같은 커밋에서 전체 회귀가 성공해야 합니다. 방법은 CONTRIBUTING.md의 "CI: 빠른 검사와 전체 회귀"에 있습니다.
- 지금 main에는 브랜치 보호도 ruleset도 없습니다. 그래서 GitHub이 이 조건을 강제하지는 않습니다. 강제하려면 저장소 관리자가 main용 ruleset에서 다음 이름을 필수 검사로 지정해야 합니다(아직 바꾸지 않음).
  - `static, evidence, renderer and build`
  - `related CPU regressions (1/6)`~`(6/6)`
  - `related browser checks (1/4)`~`(4/4)`
  - `full regression on this exact head`
