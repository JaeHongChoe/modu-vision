## Windows 텍스트 인코딩과 열린 파일 비교

`8350453`: Windows에서 Python은 인코딩을 지정하지 않으면 시스템 코드 페이지(cp1252·cp949)로 텍스트를 읽고 쓰는데, 앱은 JSON을 한글 그대로 UTF-8로 저장한다. 백엔드와 빌드·배포 스크립트의 모든 텍스트 읽기·쓰기에 UTF-8을 명시했다(키워드만 추가한 변경임을 비교로 확인). 우리가 띄우는 Python 하위 프로세스와 원격 서버 출력은 UTF-8로, 로컬 OS 도구 출력은 시스템 인코딩에 대체 문자를 허용해 읽는다. 사용자가 다른 도구로 저장한 라벨 파일은 UTF-8(BOM 허용)로 읽고, 실패하면 그 PC의 기본 인코딩이 UTF-8이 아닐 때만 그 인코딩으로 읽는다(이전 동작과 같다). 기본 인코딩을 쓰는 코드가 다시 들어오면 실패하는 검사와, UTF-8 기본값이 없는 프로세스에서 한글 프로젝트를 실행하는 검사를 추가했다.

관리 사본의 원본 확인이 경로 기준 stat과 열린 파일 기준 stat을 비교했는데, Windows는 두 값의 장치·파일 번호를 다르게 채워 모든 관리 사본이 거부되었다(hosted 실행 37014514960). 같은 방식(열린 파일 두 개)으로 비교하도록 고쳤고, 읽은 뒤 바뀐 파일은 여전히 거부한다. 크기 없는 LabelMe 파일 옆의 이미지를 열지 못하면, 디코딩할 수 없는 경우에만 라벨 없음으로 처리하고 잠긴 파일 같은 일시적 오류는 그대로 알린다(학습에 빈 마스크가 들어가지 않는다).

검증: 고정 트리에서 백엔드 전체 2790개 통과(git이 없는 내보내기 때문에 생긴 1건은 검토에서 확인), 변경 범위 443개 통과·4개 skip, Windows 작업 목록 94개를 일반·US-ASCII locale에서 모두 통과. 독립 검토 두 회차, 마지막은 승인. Windows hosted 재실행 결과 전에는 Windows 검증으로 기록하지 않는다. 남은 것: 테스트 코드의 기본 인코딩 읽기 약 810곳, 일부 라벨 읽기 경로의 엄격한 UTF-8, Pillow가 errno 없는 OSError로 알리는 잘린 헤더, Windows 작업의 Electron 단계.

## 데이터 가져오기 4단계: ZIP 가져오기, 원본 주석과 중복 기록

버전마다 원본의 주석 파일(LabelMe·COCO·YOLO)이 말하는 형식·라벨·연결 파일과 그 해시를 기록한다. 검출·세그멘테이션은 주석이 깨졌거나 모호하면 선택한 정책에 따라 그 이미지를 잘못된 항목으로 둔다(Studio 라벨이 있으면 제외하지 않는다). 폴더로 라벨을 정하는 작업은 오류를 기록만 하고 이미지를 빼지 않는다. 같은 내용의 이미지는 중복 그룹으로 묶고, 라벨이 다르거나 train/val/test가 섞인 그룹을 따로 센다. 중복은 보고만 하고 지우지 않는다. 정상 이미지가 하나도 없는 버전은 채택할 수 없다. index는 schema 3으로 올라가며 기존 schema 2 파일은 그 자리에서 테이블만 추가한다.

검증: 고정 트리(기준 + 21개 파일)에서 170개, 회귀 742개 통과·4개 skip(홈 저장소 감시 비어 있음), 화면 로직·typecheck 통과, 실제 backend 브라우저 e2e 3개(ZIP을 실제 파일 선택으로 올림, 중복, 가져오기) 통과. 현재 main(6698818) 위에서도 다시 179개(인코딩 검사 포함)와 e2e 3개 통과. 독립 검토 다섯 회차, 마지막은 승인. 남은 것: 압축 풀기를 작업 스레드로 옮기기, 일시적인 완료 실패 때 업로드를 다시 해야 하는 점, mask 주석 연결, 원본 주석 읽기의 시스템 인코딩 대체, Windows native.
